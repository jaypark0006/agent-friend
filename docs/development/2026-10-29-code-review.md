## 需要修复的发现

### R1 · P1 · LED 参数错误可以导致设备崩溃

位置：`vendor/esp-mosaico-vibe/projects/lan_screen/main/screen_interact_http.c:26–29`。

`effect` 存在时，代码先把 `cJSON_IsString(effect)` 合入 `ok`，随后仍无条件执行 `strcmp(effect->valuestring, ...)`。例如发送 `{"slot":"right","effect":123}`，`valuestring` 为 NULL，参数校验尚未返回 400 就会解引用空指针。

应在读取字符串前拒绝错误类型，并让其余解析只消费校验成功的值。这是具体输入触发的错误，不需要扩大成全接口重构。

### R2 · P1 · README 的直接烧录命令使用错误芯片和地址

位置：`README.md:127–129`；对照 `vendor/esp-mosaico-vibe/projects/lan_screen/partitions.csv:5–8`。

文档写 `--chip esp32s3 ... write_flash 0x140000`，实际目标是 `esp32s31`，应用 `ota_0` 起点为 `0x210000`。`0x140000` 位于保留的 factory 区域内。该命令可能先因芯片不匹配而被拒绝；若使用者调整芯片或强行按该地址写入，会覆盖保留固件及随后区域，而不是正确更新应用。

应删除这条安装途径，保留项目规定的官方 CLI 更新流程，并区分已有兼容分区的应用更新和首次安装/系统更新。根 README 的 ESP32-S3、屏幕型号和 PSRAM 描述也应按项目已知事实纠正。

### R3 · P2 · 设备 `/skills` 给出的协议与实现不一致

位置：固件 `main/skill.md:160–162,207–209`；对照 `main/screen_interact_http.c:17–18`、`main/screen_widget.c:300,353`、`main/screen_display.c:175`。

- HTTP LED 示例使用 `slot:"auto"`，但 REST 入口只接受 `left`/`right`，照抄会返回 400；WS `led.set` 才支持 auto。
- 确认事件示例写 `action:"confirm"`、`trigger:"left_button"`，实际发出的是 `approve`/`cancel` 和 `physical_button_left`/`physical_button_right`。

这是新 Agent 依赖设备说明接入时会直接遇到的障碍。修复时应逐项对齐真实收发字段，并补全“先订阅事件，再发布确认”的接入顺序。仅修改宿主 Skill 的措辞，无法消除设备协议说明的错误。

### R4 · P2 · 网页会把正常广播事件误当成图片上传失败

位置：固件 `main/console-api.js:140–146`、`main/screen_ws.c:33–40`。

服务端向 `/ws/frames` 同时广播 `page.changed`、`task.action`、姿态等事件；网页图片发送器在等待回执时，要求收到的每条 JSON 都包含 `accepted`。若图片 ACK 前先到一条普通事件，网页会关闭连接并报“回执缺少图片编号”，即使图片已经被设备接收。

应先按消息类型/命令分流，只让图片 ACK 完成对应发送操作，普通事件不得结算或拒绝图片请求。

### R5 · P2 · 16–64 字号接口发生兼容性回退

位置：固件 `main/screen_ui_messages.c:14–19,84`、`main/screen_font.c:24–29`；对照 `main/screen_command_json.c:9–15`。

API 仍接受并保存任意 16–64 整数字号，但渲染只选择 20、24、32 三档：发送 64 号会画成 32 号，16 号会画成 20 号。行距却继续按请求的原始字号计算，64 号消息还会出现过大的空白行距。

应恢复明确的字号语义，优先保持原 API 兼容。任何缩放方案都应以当前 Flash 字库和按需缓存为基础，并把缓存尺寸预算纳入实现；不能静默接受参数后画成另一档。

### R6 · P2 · 字库生成脚本会重新引入已修过的 Magic 错误

位置：固件 `tools/gen_flash_font.js:145,165`；对照 `main/screen_font_tables.h:6`、`main/screen_font_flash.c:181–189`。

二进制包写入 ASCII `MFNT`，小端数值应为 `0x544E464D`，当前已提交头文件也是这个值；但生成脚本输出头文件时仍写 `0x4D534346`。重新生成字库会覆盖正确头文件，下一次构建后挂载失败，字形回调得到空白点阵。

此外，脚本把 lv_font_conv 固定在本机 `/Users/qilei/.npm/_npx/...` 缓存目录，字体输入位于忽略的 `.codex-runs`，缺少可移植的依赖声明/输入准备说明。应一次修正生成源与生成产物、固定依赖版本，并允许显式传入字体与工具路径。

### R7 · P2 · 字库初始化失败没有正确传给 UI 层

位置：固件 `main/screen_font_flash.c:176–218`、`main/screen_theme.c:17–25`。

Magic 不匹配时仍初始化描述符并返回成功，后续缓存全是空白字形。若读取包头失败或分配缓存失败，则初始化提前返回；主题层忽略返回值，复制尚未填充的字体结构并标记 ready，LVGL 后续调用可能进入空回调。

应把包标识、版本/尺寸及初始化结果作为明确的加载边界；失败时给出可见错误或经过设计的最小可用字体路径，不得把失败当作成功。当前源码中没有证明 1.1.54 的现有包已经挂载失败，问题在于失败路径。

### R8 · P2 · 报错任务可能仍处于可裁决的确认态

位置：固件 `main/screen_widget.h:51–57`、`main/screen_widget.c:164–191`。

`screen_agent_pending` 检查 `!done`，没有排除 `error`。一张未决确认卡片之后上报 `error:true` 而不传 done，旧 action 会保留：任务已经被 `screen_agent_finished` 视为失败，同时又被当作等待确认，橙色优先级覆盖红色错误，按钮也仍可裁决。

应定义清楚 error、done、等待确认和恢复工作的转换关系，让失败任务退出可裁决状态，同时保留真实错误原因。

### R9 · P2 · 客户端默认任务 ID 导致不同 Agent 互相覆盖

位置：`skills/mosaico-notify/scripts/progress.py:180`、`README.md:60–80`。

省略 `--id` 时所有调用都写入 `task-1`；README 三段调用都省略了 ID。固件严格按 ID 匹配，因此两个 Agent 照着示例工作，会更新同一张卡片，标题、状态、进度和确认请求可能互相覆盖。Skill 文字要求独立 ID，客户端和入门示例却允许最容易出错的用法。

应让示例显式复用本任务的唯一 ID，并让客户端对缺失 ID 给出明确处理。ID 应包含足够的会话/轮次区分，不能只依赖 Agent 自觉选择 `task-1`。

### R10 · P2 · 确认等待的超时实现与文档不符

位置：`skills/mosaico-notify/scripts/progress.py:106–138,242–280`。

WS 路径把 socket timeout 固定为完整 timeout，每次读取不会缩短为剩余时间。临近截止收到半帧时，等待可超出总期限；完全没有事件时，socket 超时异常没有被转换成下方约定的 JSON timeout/退出码 3，而是直接抛出异常。连接失败后回落 HTTP 的路径与 WS 路径表现也不一致。

应使用单调时钟和剩余总时间，并把预期的超时/断连转换为明确结果，保留“超时不等于批准”的规则。此处没有运行等待脚本进行复现。

### R11 · P2 · 传感器 WS 存在两个任务同时写同一连接

位置：固件 `main/screen_ws.c:45–52,76`、`main/screen_network.c:344–367`。

广播工作排入 80 端口 HTTP 任务，却直接向 81 端口的传感器 socket 发送；传感器任务自己每 100ms 排入 81 端口发送快照。固定 SDK 的 `httpd_ws_send_frame_async` 在调用任务中先发帧头、再发 payload，没有把整帧自动排入所属 HTTP 任务。因此两条真实发送路径可能交错，破坏 WS 帧边界。

应由每个 HTTP server 的所属任务串行发送自己的连接，使用现有队列机制即可，不必引入新的消息总线。该发现来自线程归属及 SDK 实现，没有测量发生频率。
